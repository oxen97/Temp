# 글로벌 대응 개발 원칙 (2026-09-18)

방향은 글로벌 서비스, 1차 수익은 한국이다(REVENUE-MODEL.md 글로벌 섹션 참고).
개발 관점의 결론 한 줄: **설계는 처음부터 글로벌로 한 번에, 구현은 결제
레일 하나만 순차로.** 기관 영업은 개발이 아니므로 이 문서의 범위 밖이다.

## 1. 처음부터 그냥 같이 개발되는 것 (추가 비용 ≈ 0)

| 구성 요소 | 왜 한 번에 되나 |
|---|---|
| 에디터·뷰어·키오스크 모드 | 이미 하나고 이미 영어 UI. 국가 개념 자체가 없다 |
| 발행 파이프라인 (작품 URL·만료/아카이브·통계 수집 훅) | 어차피 한 번만 만든다. 여기에 국가별 분기를 넣지 말 것 |
| 관람 통계 수집·집계·히트맵 | 데이터에 국적이 없다 |
| 보고서 PDF **엔진** | 데이터 → 차트 → PDF 렌더 코어는 공통. 양식만 템플릿 파일로 분리(아래 규칙 3) |
| 계정 체계 | 이메일 기반 글로벌 공통. 약관·개인정보처리방침만 한/영 두 벌 |
| 가격 체계 | 통화별 가격 테이블로 설계(아래 규칙 2) |

## 2. 설계는 지금, 구현은 순차

**결제가 유일한 진짜 순차 항목이다.**

- 지금 할 일: 주문·구독·영수증(증빙)을 **추상 인터페이스**로 설계
  (아래 규칙 4). 발행 파이프라인이 이 인터페이스에만 의존하게 한다.
- 1차 구현: **한국 PG 어댑터** (카드 결제 + 세금계산서 + 현금영수증 자동
  발행 — e나라도움 정산 대응이 한국 시장의 해자)
- 2차 구현: **Stripe 어댑터** (USD 결제 + 인보이스) — 한국에서 결제 흐름
  검증 후
- 동시에 두 레일을 구현하지 않는 이유: 테스트·정산·세무 부담이 2배가
  되는데 초기에 글로벌 결제 수요는 아직 없다. 단, 인터페이스를 지금
  갈라두지 않으면 나중에 결제 코드 전체를 뜯게 된다.

PDF 보고서도 같은 패턴: 엔진은 공통으로 1번에 만들고, 템플릿은
한국(재단·e나라도움 양식) 먼저 → 영국(Arts Council England) 나중.

## 3. 처음에 지킬 규칙 4개

이 4개만 지키면 글로벌 대응에 추가 개발비가 거의 안 든다. 안 지키고
한국 전용으로 하드코딩하면, 에디터에서 겪은 일(15,000줄 단일 파일을
나중에 해체 — REFACTORING.md)을 결제·보고서에서 반복하게 된다.

### 규칙 1 — UI 문자열 분리 (i18n 준비)

- 새로 만드는 화면의 사용자 노출 문자열은 컴포넌트에 하드코딩하지 말고
  문자열 모듈로 분리한다. 지금 UI가 영어라 이미 90% 되어 있음 —
  이 상태를 유지하는 것이 규칙이다.
- 번역 시스템(i18n 라이브러리)을 지금 도입하라는 뜻이 아니다.
  "문자열이 한 곳에 모여 있으면" 나중에 어떤 방식이든 붙는다.

### 규칙 2 — 가격·통화는 테이블로

```ts
// 예시: 하드코딩 금지, 통화별 가격표
const PRICING = {
  KRW: { proMonthly: 14900, proYearly: 149000, exhibitionPass: 150000, passExtend: 50000, kioskAddon: 50000 },
  USD: { proMonthly: 12,    proYearly: 120,    exhibitionPass: 99,     passExtend: 39,    kioskAddon: 39 },
};
```

- 결제·화면·문서 어디에도 `150000` 같은 리터럴을 직접 쓰지 않는다.
- 부가세(한국 10%)·세율 처리도 통화/지역 테이블 쪽에 붙인다.

### 규칙 3 — 보고서 PDF는 템플릿 구조로

```
report-engine/          # 공통: 데이터 수집 → 차트 렌더 → PDF 출력
report-templates/
  ko-foundation.html    # 한국 재단·e나라도움 결과보고 양식 (1차)
  en-ace.html           # Arts Council England (2차)
  generic.html          # 양식 없는 지역용 기본형
```

- 엔진은 템플릿 이름만 받는다. 새 국가 = 템플릿 파일 추가.
- 렌더 기법: HTML 템플릿 → headless Chromium 인쇄 (이미 팀이 스펙 이미지
  제작에서 검증한 파이프라인과 동일).

### 규칙 4 — 결제는 어댑터 패턴으로

```ts
// 발행/구독 코드는 이 인터페이스만 안다
interface PaymentProvider {
  checkout(order: Order): Promise<CheckoutSession>;
  subscribe(plan: Plan): Promise<Subscription>;
  issueReceipt(order: Order, type: ReceiptType): Promise<Receipt>;
  // ReceiptType: "tax-invoice" | "cash-receipt" | "invoice" (지역별 구현)
}
// 구현체: TossPaymentsProvider (1차) → StripeProvider (2차)
```

- 증빙(세금계산서/현금영수증/인보이스)은 결제의 부속이 아니라
  **인터페이스의 1급 시민**이다 — 한국 수익 모델의 핵심이기 때문.

## 4. 발행 파이프라인 설계 체크리스트 (다음 개발 단계에서)

계정+저장+발행을 만들 때 아래를 처음부터 포함할 것 (나중에 덧대면 비쌈):

- [ ] 작품 URL 구조 (영구 주소, 커스텀 도메인 연결 여지)
- [ ] 발행물 상태 기계: draft → published → archived (전시 패스 만료 =
      archived 전환, 열람 가능·편집/통계 중단)
- [ ] 통계 수집 훅 (뷰어 이벤트 버스 → sendBeacon 배치 전송 지점)
- [ ] 발행물-결제 연결 (어떤 발행물이 어떤 패스/구독에 속하는지)
- [ ] Free 티어 제약 지점 (1작품 제한, 배지 렌더, 장시간 세션 확인)
- [ ] 문자열·가격·증빙이 위 규칙 1·2·4를 따르는지

## 5. 개발이 아닌 것 (이 문서 범위 밖)

- 기관 영업 (견적서 템플릿은 문서 작업일 뿐)
- 글로벌 GTM: 커뮤니티·쇼케이스(FWA/Awwwards)·졸업전 — 마케팅 활동
- 국가별 법무(약관·세무) 세부 — 해당 시장 진입 시점에
